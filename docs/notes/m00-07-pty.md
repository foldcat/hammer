# M00.07 — Spike PTY (Linux) and asynchronous process output

**Status:** done (Linux, raw syscalls via `core:sys/linux`, no new
dependencies). ConPTY/Windows deferred: this machine still has no Windows
toolchain (see the M00.06 decision note), so nothing is claimed for
ConPTY.

## What was built

`spike/pty/` contains a parent spike and a purpose-built helper child:

- `main.odin` — the parent (`build/pty_spike`). Raw Linux syscalls only:
  PTY allocation, fork/execve with controlling terminal, non-blocking
  poll-driven master reads, process-group cancellation, termios control,
  window sizing, reaping. Seven modes: `echo`, `escape`, `flood`, `kill`,
  `size`, `exitcode`, `raw`.
- `child/child.odin` — the helper the parent spawns on the slave side
  (`build/pty_child`). Speaks raw read/write syscalls so the parent has
  exact control over chunk boundaries. No shell anywhere.
- `demo.sh` — headless harness: every mode asserted, usage paths checked,
  orphan check at the end. `make.odin` gained a `pty-spike` target that
  builds both binaries.

Spike code, not product implementation (M09 owns process spawning,
M10 owns the terminal; both are informed by the findings below).

## Finding 1 — PTY allocation: unlockpt is mandatory, grantpt is a no-op

The working sequence on Linux devpts (all via ioctl, no libc helpers):

1. `open("/dev/ptmx", O_RDWR|O_NOCTTY)` — master.
2. `TIOCGPTN` — the pty index.
3. **`TIOCSPTLCK` with 0 (unlockpt) — REQUIRED.** Without it,
   `open("/dev/pts/N")` fails with **EIO** (the freshly allocated slave
   starts locked). This bit us during the spike and was confirmed
   differentially: python's `openpty` (which calls unlockpt) succeeds on
   the same mount while the un-unlocked open fails.
4. `open("/dev/pts/N", O_RDWR|O_NOCTTY)` — slave.

`grantpt` is a no-op on Linux: the devpts filesystem creates the slave
node owned by the caller (this machine mounts devpts with
`gid=5,mode=600,ptmxmode=000`; no setuid helper is involved). It is not
implemented here. Ports to other Unixes must implement the portable
`grantpt`/`unlockpt` dance; the Linux ioctl sequence above is all that is
needed here.

## Finding 2 — default line discipline transforms your bytes

Two defaults observed and handled:

- **ONLCR (output)**: a `\n` written from the slave arrives on the master
  as `\r\n` (verified: 6 bytes in, 7 bytes out). ANSI console code (M10)
  must handle CR in its stream regardless.
- **ECHO (input)**: without termios changes, bytes the parent writes to
  the master are echoed back by the line discipline — the echo scenario
  initially produced `hello\r\nhello\r\n` (one copy from input echo, one
  from the child's own write).

Both are controlled from the parent with `TCGETS`/`TCSETS` on the slave
before the child starts: `echo` mode clears ECHO; `raw` mode applies the
cfmakeraw-equivalent state (OPOST/ICANON/ECHO/ISIG/IEXTEN off, CS8) and
verifies `\n` then passes through untranslated. This is the termios
primitive M10.07 (raw input) needs, and it works from raw Odin.

## Finding 3 — escape sequences really do span chunks

The `escape` child emits `\x1b[31m` + `RED` + `\x1b[0m` + `\n` in four
writes with 50 ms gaps. With a 20 ms poll timeout and an 8-byte read cap
the parent observed exactly four reads of `5,3,4,2` bytes — the escape
sequence itself arrived split across reads — and reassembled the stream
byte-exactly. This confirms M10.01's requirement (incremental, chunk-safe
ANSI/UTF-8 decoding) is not theoretical.

The same run also proves the non-blocking claim: 8 poll timeouts elapsed
while the child slept between writes, i.e. the parent loop kept running
instead of blocking on the master fd.

## Finding 4 — the async drain pattern

`flood` had the child write 1 MiB while the parent drained the master via
`poll` + non-blocking reads into a 32 KiB buffer: 1,048,576 bytes arrived
byte-exact (pattern-sampled), in ~180 reads over ~13 ms, with zero poll
timeouts — the reader kept up with the producer without blocking. The
1 MiB was held in a growable buffer only to verify the count; a real
pipeline would cap and backpressure per SPECS.md §12.2.

End-of-output: after the child exits and the slave closes, a read on the
master returns **EIO** (verified in `exitcode` mode) — this is the
signal the async pipeline keys on to finish a job's output.

## Finding 5 — spawn, lifecycle, cancellation

- **Spawn**: `fork` + `setsid` + `TIOCSCTTY` (slave becomes the child's
  controlling terminal) + `dup2` of the slave onto fds 0/1/2 +
  `execve`. Verified end to end: the child's stdout/stderr/stin are the
  pty. argv is heap-built in the parent before the fork and passed to
  `execve`; the child's copy is discarded by exec.
- **Orphan protection**: the child arms `PR_SET_PDEATHSIG(SIGHUP)`
  immediately after fork, so it dies with the parent even if the parent
  is killed. The harness ends with a `pgrep` orphan check — clean.
- **Cancellation**: after `setsid` the child is its own process-group
  leader, so `kill(-pid, ...)` targets exactly the job. Verified with a
  child that blocks SIGTERM: group SIGTERM left it running (WNOHANG
  waitpid returned 0 — "no status change", i.e. alive), group SIGKILL
  killed it, `waitpid` reaped it with `WTERMSIG=9`. SIGKILL cannot be
  blocked, so escalation always wins.
- **Reaping**: blocking and WNOHANG `waitpid` both verified; exit codes
  round-trip (child `status 7` → `WEXITSTATUS=7`).

## Finding 6 — window size flows through the pty

`TIOCSWINSZ` set on the master is visible to the child via `TIOCGWINSZ`
on its own stdout: parent set 120x34, the child reported `cols=120
rows=34`, and the master read back the same value (pty winsize is one
value shared by both ends). That is the resize plumbing M10.07 needs.

## Not validated

- **SIGWINCH delivery** to the child (only set/get semantics verified;
  signal generation on resize not exercised).
- UTF-8 multibyte content over the pty (byte-stream verified; chunk-safe
  UTF-8 decoding is M10.01's job).
- Outputs beyond 1 MiB; canonical-mode line editing; baud control.
- ConPTY and anything Windows.

## Implications for later milestones

- M09 (spawn/lifecycle): the full primitive set — fork/execve/setsid/
  TIOCSCTTY, process groups, waitpid, kill, PDEATHSIG — is available via
  the pinned `core:sys/linux` with no new dependencies.
- M10 (terminal): confirmed requirements: incremental ANSI decoding
  (Finding 3), CR/ONLCR handling (Finding 2), termios raw/echo control
  (Finding 2), TIOCSWINSZ + SIGWINCH (Finding 6), EIO-based end-of-output
  (Finding 4), and the unlockpt step (Finding 1) in any PTY-open path.
